# 规范差异：交付形状与目录归属（delivery-shape）

## ADDED Requirements

### Requirement: 交付形状由显式映射表决定
WHEN 平台生成交付快照,
系统 SHALL 按「底座内部路径 → 交付路径」的显式映射表出路径，使交付仓库的形状与底座目录结构无关。

#### Scenario: 底座内部重排不影响交付
GIVEN 底座内部目录或模块位置发生调整，而映射表未变
WHEN 生成交付快照
THEN 交付仓库里的路径与内容形状不变
AND 已声明档位规则的落点契约（生成物路径、菜单组件解析）继续成立

#### Scenario: 映射表被改坏时当场失败
GIVEN 映射表缺了一条必要的源路径规则
WHEN 生成交付快照
THEN 系统拒绝而不是静默产出一个形状不完整的交付物
AND 错误指出是哪一条源路径没有落点

#### Scenario: 交付目录名保持稳定
GIVEN 底座内的前端目录换了名字或位置
WHEN 生成交付快照
THEN 交付仓库里的前端目录仍按映射表给定的稳定名称出现

### Requirement: 边界由目录归属承担，清单只保留例外
WHEN 判断一个文件是否进入交付,
系统 SHALL 以「是否位于底座目录内」为默认判据，黑名单只保留构建产物、本机文件与平台专属例外。

#### Scenario: 平台测试不再需要点名排除
GIVEN 平台侧的测试与夹具住在平台目录而不是底座目录
WHEN 生成交付快照
THEN 它们不出现在交付内容里，且不依赖任何点名条目

#### Scenario: 本机文件仍被跳过
GIVEN 底座目录里存在构建产物、依赖目录或本机口令文件
WHEN 生成交付快照
THEN 这些名字仍按名字被跳过
AND 用例明确断言这种跳过不依赖版本控制忽略规则（裁剪走的是文件系统遍历）

#### Scenario: 交付构建写法不再被改写
GIVEN 底座自带一份能独立启动的构建与部署配置
WHEN 生成交付快照
THEN 交付内容按原样出现，不再需要把「平台怎么构建」那几行换成别的写法
AND 原先依赖改写的场景改为由底座自身那份配置直接满足

#### Scenario: 残留兜底不随隔离撤走
GIVEN 某份交付文件仍引用平台代码、平台元数据表或平台品牌
WHEN 生成交付快照
THEN 目录隔离不被当作放行的理由，扫描仍当场拒绝

### Requirement: SQL 归属按表划分而非按文件
WHEN 划分底座 SQL 与平台 SQL,
系统 SHALL 按表与数据段的实际归属决定文件位置，并禁止在同一文件里用标记块挖出对方专属的片段。

#### Scenario: 平台专属表归平台
GIVEN 某张表只有平台功能读写
WHEN 重划 SQL
THEN 它的建表与种子出现在平台 SQL 而不是底座 SQL

#### Scenario: 登录链依赖的表留在底座
GIVEN 一张以平台命名的表实际被交付项目的登录链每次查询
WHEN 重划 SQL
THEN 它的建表留在底座 SQL
AND 文件头注释写明留在底座的原因，避免下次被当作平台专属清理掉

#### Scenario: 代码生成的表与菜单随功能归属
GIVEN 交付项目不包含代码生成能力
WHEN 重划 SQL
THEN 生成器的表与对应菜单种子归入平台 SQL
AND 底座种子文件里那两处标记块随之消失

#### Scenario: 元数据表扫描覆盖两侧目录
GIVEN 表结构分布在两个目录
WHEN 校验「带租户列的表都已登记进过滤白名单」
THEN 两个目录都被解析
AND 漏登记会被当场发现而不是静默泄露

#### Scenario: 表名清单与隔离并存
GIVEN 交付内容里出现已划归平台的表名
WHEN 生成交付快照
THEN 拒绝，并说明该表属平台侧

### Requirement: 平台专属片段必须显式标注
WHEN 平台生成交付快照（项目初始化或底座升级）,
系统 SHALL 拒绝任何命中平台专属指纹且不位于 `scaffold:platform-only` 标记区间内的行，并在错误中给出文件路径与行号。

**指纹清单的出处**：并入自原 `fix-base-upgrade-closure` 提案，收三条都落在「底座引用平台」这一真实关系上、且现有字面量残留扫描够不着的语义 —— ① 平台租户码字面量；② `lowcode:*` 权限码字面量；③ 菜单 id 命中平台保留号段。目录隔离（本提案第③刀）会把大部分适用面积消灭，剩下的用第⑤刀的单向依赖机械检查承接：那三条即为其 token 来源，不另建清单。

#### Scenario: 现状通过
GIVEN 底座目录未做任何改动
WHEN 生成交付快照
THEN 校验通过
AND 该用例覆盖搬迁后仍存留的全部标记块文件

#### Scenario: 命中但未标注
GIVEN 某个 A 档文件里新增一行命中平台专属指纹，且不在任何标记区间内
WHEN 生成交付快照
THEN 系统拒绝生成
AND 错误文本同时包含该文件路径、行号与 `scaffold:platform-only`
AND 项目初始化与底座升级两条链路同时被闸住

#### Scenario: 命中且已标注
GIVEN 同一行位于 `scaffold:platform-only` 的 start 与 end 之间
WHEN 生成交付快照
THEN 校验通过
AND 该行不出现在交付内容中

#### Scenario: 交付项目自身语义不被误伤
GIVEN 交付项目自身合法的写法：超级管理员 id 为 1、role 1 的授权行、租户号恒为 1 的判断
WHEN 生成交付快照
THEN 这些行不被判为命中平台专属指纹

### Requirement: 指纹清单的每一次收紧都必须可测
IF 平台专属指纹清单新增一项,
系统 SHALL 要求该项被至少一条命中用例与一条不误伤用例引用，否则该族测试失败。

#### Scenario: 只加指纹不加用例
GIVEN 指纹清单新增一项而没有任何用例引用它
WHEN 运行该族测试
THEN 测试失败并指出未覆盖的指纹名

#### Scenario: 放宽清单被视为改变交付口径
GIVEN 有人从指纹清单里删除一项
WHEN 运行引用该项的用例
THEN 用例失败，要求同时删除或改写其引用
AND 不允许留下引用不存在指纹的空用例
