# 规范差异：升级后半截的界面入口（base-upgrade）

并入自原 `fix-base-upgrade-closure` 提案 —— 那一半不是本重构的重复项，而是它缺的一块：第③刀之后底座升级仍是「平台推分支、人来合」，而人在界面上把升级分支变成待审请求这件事从来没有入口。分支名在本提案第③刀后按内容指纹派生（`platform-upgrade/{digest7}`），需求本身与身份机制无关，故原文照搬。

## ADDED Requirements

### Requirement: 升级分支可经界面进入合并请求
WHEN 人对一条状态为「待合并」的底座升级记录发起「生成合并请求」,
系统 SHALL 以该记录的升级分支为来源分支重算合并请求，并给出与页面发布同一套的文件清单、行内差异与确认合并入口。

#### Scenario: 正常生成
GIVEN 项目仓库状态为「就绪」
AND 底座升级已推出 `platform-upgrade/{底座身份短号}`
AND 该分支相对主干存在可合内容
WHEN 人点该动作
THEN 系统以该升级分支为来源分支、项目主干为目标分支重算
AND 展示文件数与预检结论
AND 复用既有抽屉与风琴展开，不新造布局组件

#### Scenario: 同一分支重复生成
GIVEN 该来源分支已存在一条开放的合并请求
WHEN 人再次点该动作
THEN 系统返回重算后的同一条请求
AND 界面措辞为「重算」，不得显示成新建了一条

#### Scenario: 升级分支已不在远端
GIVEN 该升级分支已被合掉或在仓库侧被删除
WHEN 人点该动作
THEN 系统原样显示后端的拒绝原因，其中包含「请重新发起一次底座升级」
AND 不改写成通用的「生成失败」提示

#### Scenario: 主干已包含全部内容
GIVEN 主干已含有该升级分支的全部文件内容（零差异）
WHEN 人点该动作
THEN 系统拒绝生成请求并说明「没有要合进主干的内容」
AND 队列中不出现一条零变更的待审条目

#### Scenario: 项目尚未就绪
GIVEN 项目的仓库同步状态不是「就绪」
WHEN 界面渲染该分组
THEN 该动作不出现（不给一颗点了只会拿报错的按钮）

### Requirement: 界面指引与可执行动作同源
WHERE 界面给出「下一步」类指引,
系统 SHALL 让该指引指向的动作在同一界面位置可直接完成，并保证指引里的分支名与该动作实际携带的来源分支名一致。

#### Scenario: 指引指向的分支就是被提交的分支
GIVEN 一次底座升级成功推出升级分支
WHEN 界面显示「下一步」文案
THEN 文案中的分支名与该动作实际发送的来源分支完全一致

#### Scenario: 从历史读数也能继续
GIVEN 底座读数里最近一条升级记录状态为待合并
WHEN 人查看该记录
THEN 同一动作出现在该行旁，效果与升级结果屏的那颗一致

#### Scenario: 合入后的读数不再提示待合并
GIVEN 该升级分支已由人确认合入主干
WHEN 人重新查看底座读数
THEN 最近一条升级记录状态为「已合入主干」
AND 待合并动作不再出现
